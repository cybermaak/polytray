## Linux lifecycle cause

The Linux preview cancellation test found the old owned renderer alive and idle at about 1.6 seconds, after its BrowserWindow had closed and a new preview process existed; it was gone by 8.5 seconds. The fixture intentionally blocks its renderer for eight seconds in a synchronous loop. `forcefullyCrashRenderer()` therefore did not meet the unchanged 500 ms OS-exit target on this runner.

The 20-cycle and multipart tests recorded `app.close()` reaching `before-quit`, `will-quit`, and `quit`, while close remained pending. At ten seconds the main Electron PID had exited, but the exact `preview.html` renderer PID from the pre-quit window snapshot remained alive in state `Il`, reparented to PID 1, with the isolated user-data directory in its command line. This happened for both tests. The installed Playwright 1.58.2 process launcher resolves its Electron close on Node's child-process `close` event; [Node documents](https://nodejs.org/api/child_process.html#event-close) that this waits for inherited stdio streams to close as well as process exit. The surviving preview renderer explains the delayed test cleanup more directly than the earlier unspecified shutdown hypothesis. [Electron's API documentation](https://www.electronjs.org/docs/latest/api/web-contents#contentsforcefullycrashrenderer) also cautions that renderer processes can be shared, so termination must prove exclusive ownership.

## Reviewed local repair candidate

The Linux candidate captures a one-time claim while a live preview `BrowserWindow` and its sole `webContents` own the PID. It requires an Electron `Tab` metric, exclusion of the main process, main and thumbnail renderers, and every other live webContents, plus a matching `/proc` start time and exact renderer executable/profile command-line tokens. Before a Linux signal, it synchronously rechecks the same generation, sender, PID, process identity, and full raw command line; missing or changed evidence rejects preview readiness or skips the signal and continues ordinary window cleanup. Linux does not use an unverified Electron force-crash fallback. Other platforms keep their existing behavior. Node lacks atomic pidfd signalling here, so a residual PID-reuse race between the final check and signal remains documented in source.

A disposable Linux arm64 container with **no host mounts** verified that normal Electron launches synthesize an exact user-data-dir renderer switch. It also exposed a one-NUL, space-separated Chromium `/proc` command line; the parser now supports that observed form while retaining exact token checks and an opaque full raw-command-line fingerprint recheck. In this container the real held-parser cancellation test passed with the old PID exiting in **24 ms**, and its existing main/thumbnail survival assertions passed. The multipart test and the 20-cycle resource test also passed; the latter used Openbox under Xvfb, matching the hosted workflow. Both sampled app closes settled promptly. These local Linux arm64 results preceded the hosted x86_64 check below.
