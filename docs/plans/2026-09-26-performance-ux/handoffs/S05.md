# S05 handoff: watcher identity ordering and recovery

## Implemented

- Watcher add/change events now commit the current file identity through `applyWatchUpdate` before metadata extraction or thumbnail scheduling. Adds use expected revision `0` when absent; later metadata and thumbnail writes use the captured file ID and content revision.
- Same-path events are serialized. Pending bursts are coalesced for 20 ms; explicit changes remain changes so the content revision advances even when the timestamp is unchanged. Unlink flushes immediately and supersedes earlier pending add/change events.
- Metadata and thumbnail work runs after the identity commit. A completion must still match the latest event generation and indexed `(id, path, contentRevision)` before it can update SQLite or publish a thumbnail-ready event. Thumbnail failures retain the indexed row and set its revision-guarded failure state.
- The accepted unavailable-measurement fallback remains in place when watcher metadata extraction fails.
- Unlink removes a row only while its deepest configured containing root still stats as a directory. Root-status transitions are reported only when availability changes. The main availability tracker retains status for roots that remain configured across watcher stop/reconfigure and forgets removed roots, so a known outage is not lost before the replacement worker's first check. One unref'd utility-process timer checks only configured roots every 500 ms; it is stopped on watcher stop/reconfigure and process exit. A false-to-true transition requests a full scan through the existing `trigger-rescan-folder` route, allowing scan coverage to prove deletions after reconnect. Initial availability does not trigger a scan, preventing scan/restart loops.
- ZIP add/change/unlink events request a rescan of the containing directory after checking configured-root containment and availability. The existing scanner's archive coverage behavior retains members on ZIP read failure.
- Watcher `FILES_UPDATED` notifications are coalesced by path in a 50 ms batch. The existing central watcher lifecycle still owns the utility process and listener set; no event forks another worker.
- The existing `polytray://local/` policy is unchanged. The real-app regression confirms an indexed watched file is readable while an unrelated unindexed file remains forbidden.

## Verification

- RED/GREEN: the new `watcherUpdates.test.ts` initially failed because the coordinator did not exist. Focused watcher update and lifecycle tests pass 13/13. They cover commit-before-enrichment, same-path coalescing/serialization, same-timestamp change and size revision advancement, stale completion after unlink, unavailable-root removal retention, pending-event invalidation, notification batching, path-map cleanup, root-poller interval ownership/teardown, offline-state retention across reconfiguration, and a throwing thumbnail persistence callback that drains/cleans without an unhandled rejection.
- `npm run build`: passed, including typecheck and Electron/Vite bundle generation.
- `npx playwright test tests/product/e2e/watcher-races.e2e.ts`: passed 1/1 on the real Electron utility-process watcher and isolated filesystem. It holds a scan at a deterministic scanner barrier while add/change/unlink events occur, verifies thumbnail readiness and protocol restrictions, confirms records remain while the root is offline, deletes one source file while offline and observes its indexed row retained until the reconnect scan completes, then stops/reconfigures while the root is still offline. An isolated-test-only gate, constrained to the configured test root and release/marker files under `POLYTRAY_PERF_SCRATCH`, makes the replacement worker write a reached marker before waiting for release; the test waits for that marker, restores the directory, then releases the worker before its first root-status check. The recovery scan is held at the scanner barrier while the stale row is asserted present, then released and checked for pruning after completion. It also exercises normal watcher reconfigure and stop/start.
- The root-poller fallback is based on E2E evidence: on the test host, renaming the configured root away did not yield Chokidar's `unlinkDir` notification. The same E2E passed after the one-timer status check was added.
