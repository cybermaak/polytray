# T04 handoff: thumbnail job coordinator

## Implemented

- `thumbnailJobScheduler.ts` now owns one priority queue and deduplicates by the full `dedupeKey` when supplied, falling back to the path for legacy requests. Manual, watch, and scan/background requests rank 3, 2, and 1. Repeated starts share a single queue drain.
- Null output and thrown errors both get at most one automatic retry. Exhausted failures update failed counts and structured thumbnail errors; cancellation is a distinct error/result and never increments failed counts.
- `enqueueBatch` provides an actionable generated `jobId`, snapshots using the frozen `BackgroundJob` shape, pause/resume/cancel, and retry of failed identities only. Pause waits for the active bounded item and retains pending work. Cancel settles consumers, aborts an exclusively owned active attempt, and waits for its safe boundary.
- Snapshots track thumbnail pending/success/failure counts; terminal state is completed/partial/failed/cancelled. Progress notifications are coalesced to at most four per second while running; initial/control/terminal states publish immediately. Recent terminal history is capped at 20 jobs and each job keeps at most 64 error details.
- `thumbnails.ts` submits each background generation batch to that coordinator instead of starting an independent sequential loop. Results still pass the current content-revision and cache-epoch checks before the database update or ready event. AbortSignal cancellation settles and removes the hidden-renderer request registry entry.
- The service exports `getThumbnailBackgroundJobs`, `onThumbnailBackgroundJobChanged`, `pauseThumbnailJob`, `resumeThumbnailJob`, `cancelThumbnailJob`, `retryThumbnailJobFailures`, and `enqueueThumbnailJob(request, settings)`. The enqueue adapter validates indexed file ID/path/revision and obtains the extension in main. Each enqueue creates a separate single-file background job; background scan batches use one grouped job. `scopePath` identifies a single-file job; grouped batches use null.
- Terminal job events publish once per terminal attempt. Retrying failures clears the terminal-event latch and publishes one new terminal outcome for the retry round.
- Pending per-identity requests are removed as soon as they settle. Successful/cancelled identities leave no per-item history; failed requests retained for explicit retry are capped at 256 per job, and displayed error details are capped at 64. Additional failures still count in `thumbnailsFailed`, but receive a non-retryable `THUMBNAIL_RETRY_LIMIT` summary because their request payloads are intentionally not retained. `getStats()` includes retained pending-item, failed-request, and error-detail counts for verification.
- Legacy thumbnail progress events include required `outcome` (`running|completed|partial|failed|cancelled`), `generated`, `failed`, `cancelled`, and `pending`; `current` equals generated successes. Only `outcome: completed` uses `phase: done`. Shared types require these values, and App renders generated, failed, and cancelled counts for terminal outcomes.
- `clearPending(predicate)` settles only matching consumers. For active tasks it decrements each removed owner's active count before resolving safe-boundary waiters; the regression covers invalidating an active paused request.

## Frozen contract limitations for coordinator wiring

- `BackgroundJobCounts` has no `thumbnailsCancelled` field. Cancellation is represented by a terminal `cancelled` state and zero pending count internally; the scheduler's local stats retain a cancelled total. If the renderer needs a numeric per-job cancelled count, the minimal contract addition is `thumbnailsCancelled: number` in the shared counts type. This worker did not edit shared types.
- `ThumbnailJobs.enqueue` has no settings or extension. The main IPC adapter must supply current normalized settings, and this service resolves the current extension from the indexed row. `requestId` remains distinct from the generated `BackgroundJob.jobId`; the one-file job is discoverable with its path in `scopePath`.
- `ThumbnailJobResult` does not return the generated job ID. The user-actionable job ID is available from background-job snapshots/events; an enqueue caller that needs immediate job control needs the minimal return shape `{ jobId, result }`. This worker did not change the frozen shared API.
- The primary candidate maps `getThumbnailJobs`, `pauseThumbnailJob`, `resumeThumbnailJob`, `cancelThumbnailJob`, and `retryThumbnailJobFailures` through IPC and preload. The aggregate `getBackgroundJobs` and `onBackgroundJobChanged` remain read/event interfaces for scan and thumbnail snapshots. Controls are intentionally thumbnail-only until S06 supplies generic job dispatch.
