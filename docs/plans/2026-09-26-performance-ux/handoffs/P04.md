## Frozen coordinator interface

Coordinator main wiring creates one restore service after the database is initialized and supplies these dependencies:

- `getRendererRevision()` returns the real current revision for all renderer-owned restore state; `getRendererState()` returns roots, collections, and complete normalized local settings.
- `acquireMutationLease(transactionId)` returns an idempotent async release callback. The coordinator implementation gates renderer settings/root/collection edits, `FileIndexRuntime` backfill, scan batch/prune commits, and watcher writes. File-index and user mutations arriving during the lease queue for replay after release. A failed or unresolved restore retains the lease and prevents automatic scan/watch/backfill startup.
- `withCommitBoundary(commit)` synchronously runs the SQLite transaction under the same coordinator gate. No SQLite transaction spans a renderer await.
- `applyRendererState(staged)` performs idempotent writes for the complete `polytray-settings`, `polytray-library-state`, and `polytray-collections` values. It must preserve the staged full settings object, including local-only fields.
- `onPendingAnnotationsApplied` publishes the browse-revision change to the renderer after the transactional pending-to-indexed merge.

The service acquires the mutation lease before the final durable browse/renderer revision check, retains it while returning the staged state, and releases it after acknowledgment and the complete journal transition. Startup calls `reconcileImport()` before any scan, watch, or scope backfill. A `blocked` recovery result must keep the same mutation gate closed and surface the recovery backup location/error through status.

The service methods are `getCurrentSnapshot()`, `previewImport(backup, currentSnapshot, options)`, `commitImport(transactionId)`, `acknowledgeImport(transactionId, rendererRevision)`, `reconcileImport()`, `cancelImport(transactionId)`, `getStatus()`, and `retryPendingAnnotations()`. The IPC adapter defines `METADATA_RESTORE_CHANNELS` for snapshot, preview, staged commit, acknowledgment, cancel, status, and retry. The renderer applies the returned `StagedMetadataRestore` before calling acknowledgment; cancel after the SQLite marker is rejected.

## Persistence and identity behavior

Migration 6 adds pending annotation rows keyed by canonical identity, durable import markers, and persisted conflicts. The file-index repository owns pending reads/upserts and one atomic `applyMetadataRestoreTransaction` that resolves the full indexed snapshot to stored path, file ID, and content revision, checks before-values, writes indexed and pending annotations, advances one browse revision if annotations changed, and records `database-applied` in the same transaction.

The journal uses synced atomic replacement and carries before/after renderer state, the P03 plan, and the pre-import recovery backup location. SQLite marker state determines abort versus roll-forward. Startup can roll forward from the durable marker even if the redundant file journal is absent; corrupt journal/backup evidence is retained and reported as blocked. Completed transactions retry idempotently.

Pending rows preserve foreign absolute paths and exact ZIP member identity. File-index commit events distinguish inserted paths with `addedPaths`; the restore subscriber applies P03's tag/note/status merge once, consumes conflict-free pending rows transactionally, and retains/report conflicts. Annotation-only writes do not emit an added-path event.

The P03 plan now carries the exact indexed row ID, raw stored path, and content revision expectations for each indexed restore target. Revision freshness is checked immediately before the transaction and those identity expectations are rechecked inside the transaction.

## Cancel/commit serialization repair

Candidate follow-up: commit operations are tracked by transaction ID from before their first await; a cancel operation is also tracked before journal I/O. Cancellation waits for an in-flight commit to settle, then removes prepared artifacts only if no SQLite marker exists. A marker-backed outcome is non-cancellable and retains its journal, backup, and lease. A commit requested during cancellation waits for that cancellation to settle before resolving the prepared plan. The blocked-journal race test pauses `prepared` journal persistence, races cancellation, then verifies the durable marker never lacks the journal/backup and the lease stays held until acknowledgment. The pre-commit cancel test continues to verify no database or recovery artifacts are created.

## Cross-platform atomic-write durability

Both the journal's async writer and the pre-import backup's sync writer continue to sync the temporary file and atomically rename it on every platform. After rename they use `directorySync.ts` to flush directory metadata where supported. POSIX directory-open/fsync/close failures propagate. On Windows, only known unsupported errors from the directory `fsync` call (`EPERM`, `EINVAL`, `ENOTSUP`, `EOPNOTSUPP`, `ENOSYS`) are skipped; directory-open, close, and other errors such as `EIO` still fail the restore. This follows Node's documented OS/device-specific fsync and platform-specific directory-handle behavior ([Node.js fs docs](https://nodejs.org/api/fs.html#fsfsyncfd-callback)) and keeps the file flush + rename durability sequence in place.

The injected directory-sync platform/filesystem tests cover both sync and async writers: Windows unsupported fsync is tolerated and handles are closed; POSIX still performs fsync; POSIX EPERM, Windows open EPERM, and Windows EIO propagate. The focused restore/journal/directory-sync/IPC suite passes **27/27**; `npm run build` passes, including typecheck.
